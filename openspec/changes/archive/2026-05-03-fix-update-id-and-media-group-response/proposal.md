## Why

PR #1 code review identified three issues: `update_id` values in `user.ts` and `reply.ts` were generated by consuming message ID counter slots (leaking IDs between two independent sequences), `sendMediaGroup` auto-responses always returned a single-item array regardless of how many media items the bot sent, and `GROUP_ANONYMOUS_BOT.is_bot: false` looked like a bug but is intentional Telegram behaviour.

## What Changes

- **`update_id` counter independence**: All `nextMessageId() + N` expressions used for `update_id` in `User` dispatch methods and `Reply.clickButton` are replaced with `nextUpdateId()`. Update IDs now come from their own dedicated counter (starting at 1 000 000), leaving message IDs unaffected.
- **`sendMediaGroup` response matches item count**: The `syntheticMediaGroup` resolver in `buildDefaultResponses` now reads `payload.media.length` from the bot's outgoing `sendMediaGroup` call and returns one synthetic `{ message_id, date }` per media item instead of always returning a single-item array.
- **`GROUP_ANONYMOUS_BOT.is_bot` documented**: An inline comment explains that `is_bot: false` is correct — Telegram sends this exact shape in real update payloads, consistent with `Channel_Bot` (id: 136 817 688).

## Capabilities

### New Capabilities

_None._

### Modified Capabilities

- `synthetic-message-responses`: The `sendMediaGroup` requirement changes from "array of length 1" to "array whose length equals the number of items in the bot's `media` payload".

## Impact

- `src/high-level/user.ts` — all `User` send/dispatch methods
- `src/high-level/reply.ts` — `clickButton`
- `src/high-level/chats.ts` — `buildDefaultResponses` / `syntheticMediaGroup`
- `tests/high-level/media-group.spec.ts` — test updated to assert length 2 for a two-item media group
- No public API surface changes; no breaking changes for consumers
